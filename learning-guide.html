    Stage 1Overview of everything

    The big picture

    What the game is, which files exist, and what each one does, before going into any detail.

    The game in one paragraph

    The player taps JOIN THE WORLD WAR, then drafts 3 of 9 houses with a budget of 999 gold. Each house has a type (Attack, Defense or Mix), a tier and a price. PREPARE FOR WAR reveals an enemy alliance. On Normal the enemy picks at random; on Hard it picks the alliance that counters yours best. FIGHT! works out each side's strength: power × (1 + type edge) × luck. Three animated rounds play, then VICTORY or DEFEAT. Wins, losses and streaks are saved in the browser.

    Three languages, three jobs

    HTML: the skeleton

    Says what exists: buttons, panels, tables, audio players. File: index.html.

    On its own it is a plain, unstyled page that can't do anything.

    CSS: the skin and armour

    Says how it looks: colours, sizes, layout, animations, phone vs PC. File: css/got-theme.css.

    It cannot react to clicks by itself, apart from states like :hover.

    JavaScript: the brain

    Says what happens: rules, maths, AI, sound, saving, switching screens. Files: js/*.js.

    It changes the HTML and CSS classes while the game runs.

    🎭 Analogy

    Think of a castle. HTML is the stone walls and rooms. CSS is the paint, banners and torches. JavaScript is the people inside: guards who open doors (buttons), a treasurer counting gold (budget), a general planning battles (AI), and a herald blowing horns (audio).

    Stage 3Background for Phases 1–4

    How the browser loads the page

    What happens between typing the URL and seeing the Iron Throne. This explains why the files are ordered the way they are.

    From URL to pixels

    RequestGET /GOT/index.html
    Parse HTMLbuilds the DOM tree
    Parse CSSbuilds the CSSOM
    Render treeDOM + styles, skips display:none
    Layoutsizes + positions
    Paint + compositepixels on screen

    The DOM (Document Object Model) is the browser's live tree of objects built from your HTML. JavaScript never edits the file; it edits this live tree. The CSSOM is the same idea for CSS rules. Each time JS changes a class, the browser repeats style → layout → paint for the affected part.

    The exact loading order of index.html

    1. Meta tags (charset, viewport, title, share preview). These have to come first because they affect how the rest is read and shown.
    2. Font preconnect + Cinzel stylesheet. Starts the connection to Google Fonts early.
    3. got-theme.css?v=50. CSS blocks rendering: the browser won't paint until it has the styles, so you never see an unstyled page.
    4. Inline script in <head>. Runs immediately, before anything is painted. It adds narrow (phone layout) and fonts-loading (page hidden) to <html>.
    5. <body> is parsed: audio elements start downloading (preload="auto"), then all the screens, buttons and panels.
    6. Scripts at the very end: data.js → audio.js → ui.js → combat.js, each downloaded and run in order. Because they come last, every element they look up already exists.
    7. Font ready (or after 2.5 s): fonts-loading is removed and the page fades in.
    💡 Why scripts go at the bottom

    A normal <script> stops the HTML parser until it has downloaded and run. If data.js were in the head, document.getElementById('start-screen') would return null because that element hasn't been parsed yet. The game would crash. At the end of the body, everything exists. (Modern alternative: <script defer> in the head does the same.)

    ⚠️ Gotcha: FOUC and layout flash

    FOUC = "flash of unstyled content". This project prevents two kinds of it: (1) the phone briefly showing the 3-column PC layout, fixed by setting .narrow in the head script before the first paint; (2) text jumping when Cinzel replaces the fallback font, fixed by keeping the page invisible until the font has loaded.

    🧠 Remember
    • Pipeline: HTML → DOM, CSS → CSSOM, render tree → layout → paint.
    • JS changes the DOM (live tree), never the HTML file.
    • CSS in the head blocks painting. A normal script blocks parsing. That's why scripts sit at the end of <body>.
    • The tiny head script runs before the first paint so the right layout and the font are ready.

    Key idea: "screens" are just shown and hidden

    There is no second HTML page. Both screens are always in the DOM; the class hidden (display: none !important) decides which one you see. This is the basic idea of a single-page app: instant switching, no reload, and the music keeps playing.

    #start-screen visible#battle-phase.hidden
    tap JOINJS swaps the classes
    #start-screen.hidden#battle-phase visible

    The same trick is used inside the war hall: the PREPARE button, the Surrender/Fight row, the Home/Battle again row, codewords and health bars all exist from the start, and JS shows the ones the current moment needs.

    Small HTML details worth knowing

    • HTML entities: &#8962; = ⌂, &#128266; = 🔊, &#128220; = 📜. A number code for any character.
    • type="button" on every button: the default type is submit, which would try to submit a form.
    • Empty containers (#draft-options, #player-roster, #stats-line) are placeholders that JavaScript fills.
    • The info tables are written in HTML by hand, so if you change a price in data.js, you must change the table too. (A possible improvement: build the table from HOUSES_DATA in JS.)
    • Corner buttons sit outside .content so the zoom animation (which scales .content) doesn't move them.

    The cascade and specificity: who wins?

    When two rules set the same property on the same element, the browser decides in this order:

    1. !importantbeats everything normal
    2. Specificityid > class > tag
    3. Source orderlater rule wins

    Specificity is counted as (ids, classes/attributes/pseudo-classes, tags) and compared left to right:

    SelectorScore
    button(0,0,1)
    .hidden(0,1,0)
    .gold-display span(0,1,1)
    #start-screen(1,0,0)
    .narrow #war-hall(1,1,0)
    💡 Why .hidden needs !important, a real example from this game

    #start-screen { display: flex } scores (1,0,0). .hidden { display: none } scores (0,1,0). The id wins, so without !important the start screen could never be hidden. The same reason explains .over-budget { color: #ff4444 !important } (it must beat .gold-display span) and .splatter-active { opacity: 1 !important } (it must beat #blood-splatter { opacity: 0 }).

    Inheritance: some properties (colour, font) pass from parent to child automatically. Here the reset sets color and font-family on * (every element) directly, and buttons use font: inherit; color: inherit to copy their parent.

    The box model

    /* The reset: the first rule every project needs */
* {
    margin: 0; padding: 0;          /* remove browser default spacing */
    box-sizing: border-box;         /* width includes padding + border */
    text-align: center;
    color: #e0e0e0;
    font-family: 'Cinzel', serif;   /* serif = fallback if Cinzel fails */
}

    Units: the most important choice for scaling

    UnitRelative toUsed for
    pxfixedhardly used (only some JS animations). Doesn't scale nicely.
    remthe root (html) font sizealmost everything. Change the root size and the whole game scales.
    emthe element's own font sizebutton padding (0.8em 2em), the breakpoint 56em

    vw / vh1% of window width / heightfluid title sizes, margins

    clamp(min, preferred, max), worked out with numbers

    html { font-size: clamp(100%, 0.55vw + 0.5rem, 150%); }
    Screen widthPreferred = 0.55vw + 8pxResult
    375 px (phone)2.06 + 8 = 10.1 pxbelow the minimum → 16 px
    1920 px (PC)10.56 + 8 = 18.6 px18.6 px

    Because nearly everything uses rem, this one line makes the whole game a bit bigger on big monitors, while text never goes below 16px. Browser zoom changes the root size too, so zooming scales the entire game smoothly.

    🧠 Remember
    • Rule = selector + { property: value; }.
    • Who wins: !important → specificity (id, class, tag) → later in the file.
    • .hidden needs !important because ids beat classes.
    • Box model: content → padding → border → margin; border-box makes width include padding and border.
    • rem everywhere + clamp() on the root = one knob that scales the whole game.
    • dvh = real phone height. cqi = container width. fr = grid share.

    CSS layout: flex, grid and layers

    How the screens are arranged: flexbox for stacks, grid for the war hall, positioning and z-index for layers on top of each other.

    Flexbox: one direction at a time

    .content {
    display: flex;
    flex-direction: column;   /* stack children top to bottom */
    align-items: center;      /* centre them horizontally */
    min-height: 100dvh;

    flex: 1;                  /* take all leftover height */
    display: flex; flex-direction: column;

    In a column flexbox, justify-content works vertically (main axis) and align-items horizontally (cross axis). In a row it's the other way round. That's the most common flexbox confusion.

    Flexbox is also used for: the roster sigils (.roster), the button rows (.action-row), card contents (.draft-card) and centring the emoji in a crest.

    Grid: rows and columns at once, used for the war hall

    gap: clamp(1rem, 3vw, 3rem);

.narrow #war-hall { grid-template-columns: minmax(0, 1fr); max-width: 28rem; }

#draft-options { display: grid; grid-template-columns: repeat(3, minmax(0, 1fr)); }
    💡 Why minmax(0, 1fr) instead of 1fr

    A plain 1fr column refuses to shrink below its widest content (a long house name), which can push the page wider than the screen. minmax(0, 1fr) lets it shrink to 0, so long words wrap instead (with overflow-wrap: anywhere). Many of the "fix overflow layout" commits were about exactly this.

    The action-bar trick: no jumping buttons

    .action-bar       { position: relative; height: 3.25rem; }

    PREPARE, the Surrender/Fight row and the Home/Battle again row all sit in the exact same spot. Only one is visible at a time. Because the bar has a fixed height, swapping them never shifts anything else on the page.

    Layers and z-index

    #live-bg, #blood-splatter { position: fixed; inset: 0; }  /* inset: 0 = top/right/bottom/left 0 = full screen */

    Safe areas (notches)

    .content {
    padding: calc(3.25rem + env(safe-area-inset-top, 0px))
             calc(1rem + env(safe-area-inset-right, 0px)) ...;
}

    env(safe-area-inset-top) is the height of the notch or status bar on phones (0 on PCs). Adding it to the padding keeps buttons tappable and visible. calc() lets you mix units: rem + px.

    Overflow

    • body { overflow-x: hidden }: no sideways scrolling.
    • #game-container { overflow: hidden; overflow: clip; }: animations that briefly scale things up never create scrollbars. clip is the stricter modern version; the line before it is the fallback for older browsers. Writing a property twice like this is a common progressive enhancement pattern: the last value the browser understands wins.
    • #info-modal { overflow: auto; overscroll-behavior: contain }: the panel scrolls inside itself, and reaching its end doesn't scroll the page behind it.
    🧠 Remember
    • Flex = one direction (stacks, rows). Grid = two directions (war hall, 3×3 cards).
    • War hall: 1fr 1.5fr 1fr on PC → 1fr on phones (via .narrow).
    • minmax(0, 1fr) stops long content from overflowing.
    • absolute is placed inside the nearest relative parent; fixed is placed on the window.
    • Layers: bg 1 · content 2 · blood 50 · icons 100 · rules 200.
    • Action bar: all button rows stacked in one fixed-height box, so nothing jumps.

    House crests: no image files at all

    Each crest is a <span class="crest"> with an emoji inside. Here are four real ones, drawn with the exact CSS from the game:

    1. Custom properties (CSS variables). JS writes style="--c1:#b3121b;--c2:#1a0204" on each crest (from colors in HOUSES_DATA). CSS reads them: radial-gradient(circle at 35% 30%, var(--c1) 0%, var(--c2) 85%). One rule, nine different crests.
    2. Perfect circle: border-radius: 50% + aspect-ratio: 1 / 1 + width: 100% (it fills whatever holds it).
    3. Depth: box-shadow: inset ... darkens the inner edge; a gold border frames it.
    4. Container query unit: the crest has container-type: inline-size, so the emoji can use font-size: 52cqi = 52% of the crest's width. Big crest, big emoji, automatically. The line before it (1.5rem) is the fallback for old browsers.
    5. Uniform silver emblems: filter: grayscale(1) brightness(1.35) contrast(1.1) drop-shadow(...). Emoji look different on Apple, Windows and Android; turning them all grey-silver makes the set look consistent.

    Transitions vs animations

    transition

    "When this property changes, glide to the new value."

    Needs a trigger (hover, a class change, JS setting a width).

    Example: .health-bar { transition: width 0.5s }. JS sets width = '45%' and the bar slides down.

    animation + @keyframes

    "Play this sequence on its own."

    Runs as soon as the element appears; can loop.

    Example: slowZoom 30s, infinite alternate, on the background.

    @keyframes slowZoom { 0% { transform: scale(1); } 100% { transform: scale(1.15); } }
#live-bg { animation: slowZoom 30s infinite alternate ease-in-out; }

@keyframes fadeIn { from { opacity: 0; transform: translateY(0.75rem); } to { opacity: 1; transform: none; } }
#start-screen, #battle-phase, .action-row, ... { animation: fadeIn 0.4s ease backwards; }
    💡 Why fadeIn plays again every time a screen appears

    An element with display: none isn't rendered at all. When .hidden is removed, the element is rendered again, which restarts its CSS animation. So every time JS shows a screen or button row, it fades in for free, with no JS animation code.

    💡 Why animate transform and opacity

    The browser can animate these on the GPU without redoing layout, so they stay smooth even on cheap phones. Animating width or top forces layout on every frame. (The health bar animates width, which is fine for one small element.)

    The blood flash, in three properties

    #blood-splatter { background: radial-gradient(circle, transparent 20%, rgba(60,0,0,0.8) 100%);

    The strength formula

    calculatePowersum of power
    × (1 + typeEdge)±5% per matchup
    = strength
    × luck0.85 – 1.15
    finalhigher wins
    function typeEdge(army, foe) {
    let edge = 0;
    army.forEach(a => foe.forEach(f => {          // every pair: 3 × 3 = 9 matchups
        if (BEATS[a.role] === f.role) edge += TYPE_EDGE;       // mine beats theirs
        else if (BEATS[f.role] === a.role) edge -= TYPE_EDGE;  // theirs beats mine
    }));
    return edge;
}
function strength(army, foe) { return calculatePower(army) * (1 + typeEdge(army, foe)); }

    Worked example 1: pure Attack vs pure Mix

    You pick Targaryen (A, 3) + Dothraki (A, 2) + Dornish (A, 1) = 950G, power 6. The enemy has Pure Mix (power 6).

    vs Storm (M)vs Iron (M)vs Vale (M)
    Targaryen (A)+5%+5%+5%
    Dothraki (A)+5%+5%+5%
    Dornish (A)+5%+5%+5%

    Your edge = 9 × 5% = +45% → strength 6 × 1.45 = 8.7. Enemy edge = −45% → 6 × 0.55 = 3.3. Even with the worst luck for you (8.7 × 0.85 = 7.4) and the best for them (3.3 × 1.15 = 3.8), you win. Against Pure Defense the numbers swap, and you can't win.

    Worked example 2: a balanced army

    Stormlanders (M, 3, 400) + Dothraki (A, 2, 300) + Night's Watch (D, 2, 280) = 980G, power 7. Against Pure Attack:

    • Storm (M) vs 3× A: Attack beats Mix → −15%
    • Dothraki (A) vs 3× A: same type → 0%
    • Night's Watch (D) vs 3× A: Defense beats Attack → +15%
    • Total edge = 0%. The same happens against Pure Defense and Pure Mix.
    💡 Insight: one of each type cancels every counter

    An army with one Attack, one Defense and one Mix always has a 0% edge against the three pure enemy alliances. It wins one third of the matchups and loses one third. So Hard mode can't counter it, and 7 power beats the enemy's 6 most of the time: 7 × 0.85 = 5.95 at your worst vs 6 × 1.15 = 6.9 at their best, so luck can still flip it. Finding things like this is what game balancing is about.

    Luck

    const pFinal = strength(playerRoster, enemyRoster) * (Math.random() * 0.3 + 0.85);

    Math.random() gives a number from 0 up to (not including) 1. × 0.3 → 0 to 0.3. + 0.85 → 0.85 to 1.15. Each side rolls separately.

    Enemy AI

    function generateEnemyRoster() {
    // ids → full house objects
    const combos = ENEMY_COMBOS.map(c => c.ids.map(id => HOUSES_DATA.find(h => h.id === id)));
    let chosen;
    if (difficulty === 'hard') {
        chosen = combos.reduce((best, c) =>
            strength(c, playerRoster) - strength(playerRoster, c) >
            strength(best, playerRoster) - strength(playerRoster, best) ? c : best);
    } else {
        chosen = combos[Math.floor(Math.random() * combos.length)];   // 0, 1 or 2
    }
    enemyRoster = chosen;
    enemyGold = STARTING_GOLD - chosen.reduce((sum, h) => sum + h.cost, 0);
}

    Hard mode scores each alliance as (enemy strength − your strength) and keeps the highest. reduce here means "walk the list and keep the best one so far". For your pure Attack army from example 1:

    Enemy optionEnemy strengthYour strengthScore
    Pure Attack6.06.00
    Pure Defense8.73.3+5.4 ← chosen
    Pure Mix3.38.7−5.4

    This is the simplest kind of AI: try every option, score it, keep the best. It's possible here because there are only 3 options.

    formatEdge(0.15) → "+15%": Math.round(edge * 100) plus a "+" for positive numbers. It's shown in the battle log after PREPARE.

    🧠 Remember
    • final = Σpower × (1 + edge) × luck, luck = Math.random() * 0.3 + 0.85.
    • Edge = 9 matchups × ±5% → between −45% and +45%.
    • Normal AI: Math.floor(Math.random() * 3). Hard AI: highest (enemy − you) via reduce.
    • One of each type = 0% edge against every pure alliance.
    • The most power any affordable army can reach is 7 (e.g. 3+2+2 or 3+3+1, like Stormlanders + Unsullied + Riverlands = 980G). Power 8 would cost at least 1130G.

    Making a war horn from maths

    function horn(t, freq, endFreq, dur, vol) {
    // 1. volume envelope: swell in 0.25 s, hold, fade out in the last 0.4 s
    out.gain.setValueAtTime(0.0001, t);
    out.gain.exponentialRampToValueAtTime(vol, t + 0.25);
    ...
    // 2. low-pass filter "opens" (200 → 900 Hz) then closes: like breath filling a horn
    filter.type = 'lowpass';
    // 3. two sawtooth waves 7 cents apart: the tiny mismatch makes a thick, brassy sound
    [0, 7].forEach(cents => { osc.type = 'sawtooth'; osc.detune.value = cents; ... });
}
    • Oscillator = a pure tone generator. Sawtooth is buzzy and rich; sine is smooth.
    • Low-pass filter removes high frequencies, which turns the harsh saw into a mellow horn.
    • Envelope = how volume changes over a note's life.
    • Exponential ramps: ears hear volume and pitch on a log scale, so exponential sounds natural. They can't reach exactly 0, hence 0.0001.
    • Drum: a sine dropping 110 → 40 Hz in 0.5 s with a fast fade = a deep boom.
    • Victory: drum, drum, horn on D (146.8 Hz), then a higher horn on A (220 Hz), rising and triumphant. Defeat: a boom and one long horn sliding down from A (110 Hz) to D (73.4 Hz), sinking.

    Responsive layout and motion

    How one page works on phones, tablets and PCs, why nothing "jumps" when the window resizes or zooms, and how motion respects the user.

    The breakpoint

    One rule: narrower than 56em (≈ 896 px at 16 px, more if the root font is bigger) → one column. Using em means a PC zoomed in a lot also switches to the phone layout, which is exactly what you want.

    Why a .narrow class instead of a CSS media query

    A media query in CSS switches instantly, with no chance to animate. This project moves the decision into JS: JS watches matchMedia('(max-width: 56em)') and toggles .narrow on <html>, which gives it the moment to morph panels to their new spots.

    Before the first paint: the head script

    (function () {
    var root = document.documentElement;                              // the <html> element
    root.classList.toggle('narrow', matchMedia('(max-width: 56em)').matches); // right layout from frame 1
    root.classList.add('fonts-loading');                             // CSS: opacity 0
    var show = function () { root.classList.remove('fonts-loading'); };
    if (document.fonts && document.fonts.load) {
        Promise.all([document.fonts.load('400 1em Cinzel'), document.fonts.load('700 1em Cinzel')]).then(show, show);
    } else { show(); }
    setTimeout(show, 2500);                                             // never wait forever
})();

    It uses var and function (old syntax) on purpose, so it runs in every browser. It checks that document.fonts exists before using it (feature detection). Because .content has transition: opacity 0.5s, removing the class makes the page fade in.

    syncLayout(): the decision tree

    window resized / query changed
    already the right layout? → stop
    reduced motion or tab hidden? → switch instantly
    cancel any zoom animation
    browser has startViewTransition? → View Transition morph
    else → FLIP fallback morph (Firefox)

    It listens to both the query's change event and resize, because some browsers don't fire the change event reliably.

    View Transitions: the browser does the morph

    document.startViewTransition(applyLayout);   // snapshot → change → animate between snapshots

/* CSS: name the panels the browser should track */
#player-side { view-transition-name: player-side; }
::view-transition-group(*) { animation-duration: 0.45s; animation-timing-function: cubic-bezier(0.2, 0.8, 0.2, 1); }

    The browser takes a picture of every named panel, applies the new layout, then animates each picture from its old box to its new box. transition.ready.catch(() => {}) ignores the harmless error when a newer resize interrupts the animation.

    FLIP: the classic hand-made morph

    Firstmeasure each panel
    Lastswitch layout, measure again
    Invertoffset = old − new
    Playanimate offset → 0
    const before = panels.map(el => el.getBoundingClientRect());   // First
applyLayout();
panels.forEach((el, i) => {
    const after = el.getBoundingClientRect();                  // Last
    const dx = before[i].left - after.left, dy = before[i].top - after.top;   // Invert
    el.animate([{ transform: `translate(${dx}px, ${dy}px)` }, { transform: 'none' }],
               { duration: 450, easing: 'cubic-bezier(0.2, 0.8, 0.2, 1)' });   // Play
});

    element.animate() is the Web Animations API: keyframes from JavaScript.

    Smooth browser zoom (Ctrl + / Ctrl −)

    Browser zoom redraws everything at the new size instantly, which feels like a jump. The trick:

    1. Zoom changes window.devicePixelRatio (e.g. 1 → 1.25) and fires resize.
    2. startScale = lastRatio / newRatio = 1 / 1.25 = 0.8.
    3. Instantly set transform: scale(0.8) on .content (no transition), so it looks the same size as before.
    4. Call getBoundingClientRect() to force a reflow, so the browser applies the 0.8 right now.
    5. Turn the transition on (0.35 s) and remove the transform → it glides to its real new size.
    6. On transitionend, remove the inline transition.

    transformOrigin is set to the middle of what's on screen, so the zoom grows from where you're looking.

    Smaller motion details

    • CSS transitions on font-size, padding, gap, letter-spacing: sizes that follow the window ease into place.
    • prefers-reduced-motion: reduce: CSS turns off every animation and transition; JS skips the zoom and morph. People with motion sickness set this in their OS.
    • @media (hover: none): on touch screens hover effects would "stick" after a tap, so lift effects are cancelled.
    • touch-action: manipulation: no 300 ms double-tap delay.
    • text-size-adjust: 100%: phones don't enlarge text on rotation.
    • Hidden tab: syncLayout switches instantly when document.hidden, so nothing animates where no one can see it.
    🧠 Remember
    • Breakpoint 56em; JS toggles .narrow so the switch can animate.
    • Head script sets .narrow and hides the page until the font loads (2.5 s max).
    • Morph: View Transitions if supported, else FLIP (First, Last, Invert, Play).
    • Zoom: scale to the old size → force reflow → transition to the new size.
    • Respect prefers-reduced-motion and hover: none.

    The caching problem and cache busting

    Visit 1browser saves got-theme.css
    You push a fixsame file name
    Visit 2browser reuses the OLD copy
    Fix: ?v=51new URL = fresh download

    Browsers cache files by their full URL. got-theme.css?v=50 and got-theme.css?v=51 count as different files, while the server ignores the ?v= part and serves the same file. Changing the number forces everyone to download the new version.

    tools/bump-version.mjs, line by line

    import { readFileSync, writeFileSync } from 'node:fs';       // Node's file-system functions
const file = new URL('../index.html', import.meta.url);   // path relative to THIS script, wherever you run it
const html = readFileSync(file, 'utf8');
const versions = [...html.matchAll(/\?v=(\d+)/g)].map(m => Number(m[1]));  // every number after ?v=
if (versions.length === 0) { console.error('No ?v=N links found'); process.exit(1); }
const next = Math.max(...versions) + 1;                    // highest + 1
writeFileSync(file, html.replace(/\?v=\d+/g, `?v=${next}`)); // replace all
console.log(`index.html: ${versions.length} links now use ?v=${next}`);
    Deep dive: reading the regular expression /\?v=(\d+)/g
    • \?: a literal "?" (escaped, because ? alone means "optional").
    • v=: the literal text.
    • (\d+): one or more digits, captured as group 1 (m[1]).
    • g: global; find every match, not only the first.

    .mjs tells Node the file is an ES module, which is what allows import and import.meta.url.
